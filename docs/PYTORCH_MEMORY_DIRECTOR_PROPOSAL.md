# Camix：PyTorch 音视频记忆导播模型方案

> **历史文档说明**：下文保留 2026-11-11 的最初提案，包含尚未实施时的状态和候选架构，不代表当前项目仍未实现训练。当前实现与边界以 [V1 契约](MODEL_CONTRACT.md)、[V2 基础指南](V2_FOUNDATION_GUIDE.md) 和 [V2 研究链路指南](V2_STAGES_GUIDE.md) 为准。

- 日期：2026-11-11
- 状态：**拟议方案，待评审**。尚未实施训练工程，尚无真实训练权重或 iPad 性能结论。
- 本次交付：训练、数据、带记忆推理、Core ML 导出和验收方案；不改现有节目切换行为。

## 1. 目标与非目标

目标：持续接收多机位真实音视频，从上下文和历史中学习各候选的播放价值，以及相对保持当前节目的切换收益。

明确要求：

1. 不预设“会议／教学／体育”等场景分类，不输出场景名。
2. 不把音量、人体、构图等手写权重作为训练答案。
3. 最终输出连续价值／收益，不输出固定相机身份的分类结果。
4. 只看当前已收到的数据和过去的历史；不使用未来画面、未来讲话或后期才能获知的信息。
5. 支持保持当前镜头，而不是自动轮播。
6. 内容判断由模型学习；人工接管、实际媒体有效性、执行互锁由程序保证。

非目标：第一版不承诺未知场景全覆盖、不做直播中自动更新权重、不提供无限记忆或指定人物的永久身份识别。

## 2. 推荐架构

采用轻量双层循环记忆作为首版基线：

实时图像／PCM -> 时间对齐及编码 -> 各机位记忆 -> 跨机位融合＋导播记忆 -> 价值／收益 -> 执行校验 -> PGM。

### 2.1 感知编码

- 视频编码器：先以可导出的小型 CNN（例如 MobileNetV3 系列）做工程基线；再比较更通用的视觉表征。不能把工程基线等同于最终语义能力。
- 音频编码器：使用真实 PCM 或由其生成的因果 log-Mel 特征；优先评估许可清楚、可转换的轻量预训练表征，不只输入电平或 VAD 单值。
- 多模态融合：网络学习不同信息在当前上下文中的价值；没有固定“音频 35%、构图 25%”公式。
- 特征提取器、前处理及策略权重均版本化。冻结编码器缓存训练特征，是第一阶段的成本控制方案；后续才考虑联合微调。
- 如口型与声音对应是关键能力，另行验证高频面部时序分支；不能默认低频整图表征已经解决主动说话人检测。

### 2.2 三种记忆

| 记忆 | 首版实现 | 目的与边界 |
|---|---|---|
| 机位短时记忆 | 每路一个共享参数的 GRU 隐状态 | 聚合此前画面、声音和运动变化；隐状态不是可解释的完整录像 |
| 全局导播记忆 | 一个全局 GRU 隐状态 | 综合各路候选及真实节目历史，学习保持与切换节奏 |
| 可审计事件历史 | 有界的已执行节目事件缓存，模型读取其编码 | 保留人工 TAKE、实际 PGM 改变、时间和必要内容摘要，弥补循环隐状态对长时事实的局限 |

首版建议数值（均为待验证预算）：每路隐状态 128 维、全局隐状态 256 维、最多 4 路槽位、最近 16 条有效节目事件。事件覆盖多长时间取决于实际事件密度，不承诺 GRU 能可靠记住几分钟全部细节。

GRU 是首版工程选择，不是最终架构承诺。若记忆收益不足，再对比有限缓存的因果注意力或 TCN；不直接搬入大型语言模型。

## 3. 推理接口与数值含义

### 3.1 对 App 的接口

流式模块持续接收：

- 视频帧、机位 ID、捕获／接收时间和旋转信息；
- 音频 PCM、采样率、机位 ID、片段起止时间；
- 真实 PGM ID、人工接管状态、转场状态；
- 已提交成功的节目事件，不是只记录模型“想切什么”。

模块周期性输出候选数值与对应时间。Core ML 文件不负责连接 WebRTC 或解码网络协议。

### 3.2 单步模型契约

建议先固定最大槽位并用 mask 区分，不把固定槽位当作实际设备身份：

| 输入 | 示例 | 说明 |
|---|---|---|
| 视频 | 最新帧张量；统一尺寸，记录原始朝向 | 对应真实画面，不是手填评分 |
| 音频 | 最近约 1 秒的因果 PCM／log-Mel 窗口 | 持续采集，前处理约定必须训练推理一致 |
| 模态有效性及 age | 每路视频／音频分开标记 | 缺失、迟到不能伪装成新数据 |
| 当前节目及持镜时间 | 运行时机位映射与持续时间 | 必须来自真实已提交的 PGM |
| 事件历史 | 有界的实际节目事件特征 | 不包含未来信息 |
| h_camera_in | [4, 128] | 各机位上一步记忆 |
| h_director_in | [1, 256] | 全局上一步记忆 |

输出：

- `keep_value`：保持当前镜头的偏好价值；
- `take_value[4]`：切到各候选的偏好价值，包含历史和切换时机的影响；
- `switch_gain[i] = take_value[i] - keep_value`；
- `h_camera_out`、`h_director_out`：下一步记忆。

这些值不是百分比、实测节目收益或校准后的可靠概率。排序训练本身不能保证统一绝对尺度，执行门槛需基于验证集的错切／漏切成本校准。首版不凭空提供一个未经校准的“confidence”。

KEEP 是价值比较的参考项，不是场景类别。当前节目机位不再作为“切到自己”的候选。

### 3.3 分包与一体化

PyTorch 中保留完整音视频编码与融合计算路径。部署可先分为视频编码器、音频编码器、记忆策略三包，方便逐段验证和调度；单包多输入是否可行以早期导出实验为准。

交付不能只有一个输入合成 `v0/a0` 的回归模型：必须同时交付真实媒体前处理、编码器、策略及输入协议。分包不意味着模型已经原生接收一个网络流地址。

## 4. 记忆生命周期

1. 新建／加入新房间：清空会话记忆。
2. 同一房间正常连续推理：传递隐状态，不在每次预测时清零。
3. 机位重连或媒体代次变化：清空该机位缓存与机位状态；保留仍有效的其他机位和会话事件。
4. 槽位顺序变化：同步重排隐状态、mask、节目引用；绝不把 A 的状态交给 B。
5. 人工接管：记忆仍可随真实音视频更新，但不执行模型动作；记录实际人工节目事件。
6. 换模型、切换权重版本或离线回放 seek：重置／按历史重新预热，不混用不兼容状态。
7. 一次只允许一个策略步进更新同一份会话状态。提交前检查房间、机位及节目版本；过期动作丢弃。

第一版优先用显式状态输入输出，便于对齐 PyTorch 与 Core ML、调试及拒绝过期结果。后续才考虑 MLState。显式传递状态仍是带记忆模型，不等于每步独立的无记忆回归。

长期个人导播风格应通过经审核的偏好数据和后续权重／配置更新体现，不把上一场 GRU 隐状态直接带到下一场充当永久记忆。

## 5. 数据采集

每场至少保存：

- 所有候选机位同步视频和独立音轨，不只是最终成片；
- 机位到导播台统一时间轴的映射、捕获与接收时间；
- 当前真实 PGM、实际人工 TAKE／接受推荐／拒绝与纠正；
- 输入迟到、掉帧、离线、重连和手动接管状态；
- 前处理、编码器和模型版本。

现有文本日志可用于动作索引和复盘，但缺少同步原始内容，不能单独训练真实多模态策略。

### 5.1 现有音频链路的前置工作

目前 AI 消费的是各机位电平遥测，WebRTC 的音轨 focus 会随 PGM 启停远端音轨。最终节目混音不能反推回所有机位的独立声音。

需要先验证两条路径之一：

- 机位端在原始麦克风 PCM 上生成带时间戳的音频特征并回传；训练保留可复现原始音频；
- 或验证／扩展导播端的混音前独立 PCM 接口。

不能声称现有电平数据已经满足原始音视频模型输入。

### 5.2 不标场景，标偏好与行为

- 导演示范：保持、实际选了哪路、何时切；
- 成对偏好：此时更愿意保持还是切到某路，两个候选哪个更适合；
- 有可信连续人工评价时可附加数值评分；
- 记录不确定／多个都合理，避免把所有没选机位都标成错误。

普通预览点击不作为已上节目的标签。未被纠正的 AI 决策不自动成为正确训练答案。无人操作也不自动等于正确保持。

## 6. PyTorch 训练方法

### 6.1 分阶段

A. 冻结编码器，缓存真实特征，训练机位／全局记忆和价值头。

B. 用人工选择与偏好训练排序：让被认可的节目动作价值高于较差动作；KEEP 也参与比较。有可信数值评价时再加入回归损失。

C. 影子运行收集错切／漏切和人工纠正，再做离线迭代。必要时解冻部分编码器。

不使用固定旧权重公式生成奖励，不让未验收权重在真实节目中随机探索。

### 6.2 时序采样

- 按场次组织连续片段，避免把随机独立窗口的隐藏状态串起来。
- 首版可试 4 秒状态预热＋16 秒计算损失；这是采样起点，不是已验证的最佳上下文。
- 同一场次连续 chunk 可以延续状态并截断梯度；跨场次清空状态。
- 训练中加入真实迟到／缺失、机位槽位置换、可用机位数量变化；窗口内的机位、状态和标签映射一致。
- 禁止双向循环、未来注意力、居中使用未来音频窗口等信息泄漏。
- 优先使用实时导演示范；后期成片的切点可能利用未来信息，不能无检查地当作实时可实现的标签。

### 6.3 验证划分

按完整场次、场地和人员分组留出。不得将同一场连续相邻帧随机拆成训练／测试并当作泛化证明。

验证时闭环运行：模型以上一步真实提交或模拟执行后的 PGM 为下一步输入，不能每个时刻强制回到人工正确答案。

## 7. Core ML 导出

### 第一阶段：显式状态

导出单步网络，隐状态作为普通张量输入和输出；App 保存并在下一步传回。训练与推理使用同一套门控更新公式。

尽早验证 GRU／融合算子、前处理和输出类型。必要时把单步 GRU 拆为线性层、sigmoid、tanh 等等价计算再导出，而不是预设任意 Python 动态路径都可转换。

交付：

- `VideoEncoder.mlpackage`（分包方案）；
- `AudioEncoder.mlpackage`（分包方案）；
- `DirectorStep.mlpackage`；
- 前处理和状态 schema、版本与校验信息；
- Swift 流式运行时、对齐缓冲和状态管理；
- PyTorch/Core ML 序列一致性报告。

以上为拟议产物，不是当前已生成的模型。

### 第二阶段：MLState 优化

若有必要，再把可用的 buffer 转成 Core ML state。目标系统和算子必须符合支持条件。MLState 是运行状态，不会让模型自动训练或无限记忆，且必须避免并发读写同一状态。

先做 Float32 对齐，再测 Float16 的误差与切播差异；量化不作为第一步。

## 8. 实时运行预算

先以 2 路真实机位为首轮验收，最大 4 路作为候选扩展目标：

- 视频语义分支起步约 5 FPS／路；
- 音频连续进入，缓存因果音频上下文；
- 策略约 200 ms 更新一次；每次更新不是每次都切播；
- 缓存有界，超过预算时丢旧视频，不无限排队；
- 模型、隐藏状态和提交路径串行管理，主线程不执行重推理。

这些是拟定设计参数，不是 iPad 实测性能承诺。必须测捕获、网络、对齐、编码、策略和切换执行的端到端 P50/P95，以及长时间内存、温度、功耗。

## 9. 必须证明“记忆有用”

1. 带记忆 vs 每步清空记忆：在历史确实影响人工偏好的测试集上比较。
2. 当前音视频相同但合法历史不同：对人工标注认为决策应不同的样本检验，不强迫所有历史变化都导致不同动作。
3. 整段 PyTorch 前向 vs 单步状态传递的一致性。
4. PyTorch vs Core ML 连续长序列：检查数值漂移、近门槛动作差异和状态更新，不只测试一帧。
5. 原始序列未来部分改变，不得影响此前输出，验证因果性。
6. 重连／换槽／人工接管／新房间后，不能串机位或串场记忆。
7. 真实多样现场里，记忆模型必须比无记忆和现有规则基线更值得人工接受。

## 10. 评价指标

- 人工偏好接受率与候选排序；
- 错切、漏掉关键内容、切点提前／滞后；
- 连续无意义跳切及人工接管次数；
- 空间、人员、内容变化后的泛化；
- 同步误差、断流、噪声下的可靠性；
- 多路端到端延迟、长时间资源使用。

不以合成数据准确率、单帧分类准确率或仅模型推理时间宣布导播产品验收。

## 11. 工程模块（建议）

训练侧：数据规范／校验、同步重放、编码器、带记忆策略、时序采样、偏好损失、训练／评估、Core ML 导出与对齐测试。

App 侧：逐路媒体输入、独立音频通路、时间映射、特征缓存、推理与状态 Actor、影子日志、统一节目提交适配。

既有 `AutoDirectorCoordinator` 可保留会话编排职责；旧 `SceneScorer`／`SwitchDecisionEngine` 是对照和故障回退，不伪装成已学习策略。保留 `ProgramSourceCoordinator.requestSwitch` 为统一提交入口，人工 TAKE／采用推荐／AI 提交都进入权威节目事件流。

## 12. 里程碑与通过条件

| 阶段 | 产物 | 进入下一阶段的条件 |
|---|---|---|
| M0 接口／导出尖峰验证 | 原始媒体前处理、最小记忆网络、显式状态导出、Swift 单步加载 | 同一序列前向对齐，连续步进／重置正确，算子可部署；随机权重只能证明工程链路 |
| M1 真实采集闭环 | 同步媒体、权威节目事件、审核和重放 | 数据可重放，独立音频可用，时间一致，无未来泄漏 |
| M2 学习基线 | 无场景类别的记忆价值模型与无记忆对照 | 留出场次里有真实收益，而不只是拟合训练集 |
| M3 iPad 影子运行 | 同时记录候选动作、状态和人工反馈，不实际切节目 | 质量和整机资源预算达标，故障可解释 |
| M4 有限自动切播 | 可随时人工接管、可回退的试运行 | 错切、漏切、记忆和长时负载均达到约定验收标准 |

没有真实数据前不承诺训练工期、准确率、所有场景覆盖或实时帧率。应先做 M0/M1，而不是先投入大规模训练。

## 13. 本方案能承诺与不能承诺的内容

能作为工程目标：搭建数据、PyTorch 训练、带记忆步进、Core ML 导出和实时 App 接入框架。

尚不能声称完成：训练好的真实权重、可靠跨场景效果、长期记忆质量、iPad 多路实时性能。

“长期记忆”不是持续保留所有视频，也不是模型会在直播里自动更新参数；权重更新必须离线审核和回归测试。
